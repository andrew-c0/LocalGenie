## Product
- LocalGenie = Tauri 2 desktop UI over Qualcomm's GenieX CLI (`geniex`), which runs local LLMs on CPU/GPU/NPU. Primary target: Windows ARM64.
- Model path for Hugging Face GGUF: the app downloads the file itself (`download_file`, resumable via `<file>.part` + HTTP Range), downloads its sidecars first, then imports with `geniex pull <repo>:<precision> --model-hub localfs --local-path <dir>` (`import_gguf`). Hub pulls are no longer used by the app.
- Qualcomm AI Hub code is legacy-in-progress, not to be expanded: `list_aihub_models`, `AihubModel`, `ModelInfo.source = "aihub"`, the "qualcomm" browse area (HF `author=qualcomm` intersected with `geniex model list`, `compatibleNames`). The compat badge input `assetCompat` is never populated (no caller of `setAssetCompat`).
- Unit tests: vitest (`npm test`), files `*.test.ts` in `utils/` and `services/database.test.ts`. Rust: inline `#[cfg(test)]` modules (`cargo test`), including the migrations, `model_settings.rs`, `model_capabilities.rs`, `capability_scan.rs`, `commands/attachments.rs`, `chat_helpers.rs`. No UI tests. Backlog: `tasks.md` (user-owned).

## Stack
React 19 + TS 5.8 + Vite 6, Fluent UI v9 (`@fluentui/react-components`, `@fluentui/react-charts` for the sidebar usage chart), zustand 5, react-router-dom 7 (MemoryRouter), react-markdown + rehype-highlight. Biome for lint/format. Rust: tauri 2 (`tray-icon` feature; `tray.rs`), tauri-plugin-shell (capability `shell:allow-open` only; the GenieX CLI is run from Rust, not via the shell plugin), tauri-plugin-dialog (`dialog:allow-open`, used by `pick_text_file` and `pick_attachment`), sea-orm 1 (SQLite), tokio, reqwest, sysinfo, base64 0.22 (probe and attachment data), image 0.25 (`jpeg`, `png`, `webp`; attachment scaling, uncommitted). Dev port 1420; GenieX server default port 18181.
Window: frameless (`decorations: false`, background `#292929`); the custom `shell/TitleBar/TitleBar.tsx` provides the chrome. Window-control permissions are in `src-tauri/capabilities/default.json`.
CSP (`src-tauri/tauri.conf.json`): `connect-src 'self' http://127.0.0.1:* ws://127.0.0.1:*` only. Webview `fetch` to huggingface.co is therefore not allowed as configured (see known-issues). Rust-side `reqwest` calls are not subject to CSP.

## Events (verified by grep of `emit`/listeners)
- `download-progress` `{ id, file, received, total, speed }`, `{ ..., complete: true }`, `{ id, file, cancelled: true }`. `id` = Hugging Face repo id (download id).

- `server-stopped` (no payload; `useModelLoader`): emitted only when the `geniex serve` child exits without a user stop. Stop and unload take the PID out of state before killing, so they do not emit it. `server-log` `ServerLogLine` (`ServerLogsCard`), `geniex-update-progress` `{ message }` (`CliUpdateCard`).
- `capability-scan-progress` `{ model, key, index, total }`: emitted by `scan_model_capabilities` before each setting is probed; listened to in `useCapabilityScan.ts`. Each decided result is also written to the server log as a `[probe]` line (`logs::record`).

## Key flows
- GGUF download: `HubModelDetail` -> `downloadStore.enqueue(variant)` (status `queued`) -> `useDownloadManager` effect -> `runGGUFDownload` (`downloadPipeline.ts`): `download_file` for each sidecar (best-effort; a cancel stops the pipeline, other failures are skipped) -> `download_file` for the main file (`.part`, Range resume, cancel via `cancel_download`) -> `import_gguf(..., sidecarPaths)` (`model-pull-start` sets `importing`; the import moves the sidecars, then the main file, into `<Downloads>/<base-model>/`, then `geniex pull`) -> `delete_directory(<folder>)`. `model-pull-complete` sets `finished` and runs `refreshAfterImport` (downloaded-model row from Hub `context_length` or DB fallback, then CLI model list refresh). Cancel of a queued entry removes it; of an active entry calls `cancel_download`. Resume = `enqueue` again; the `.part` file is reused. Other failures set `error`.
- Sidecar choice (`hubModels.ts` `pickSidecars`): one `mmproj` and one `mtp` per variant, the one whose precision matches the variant, else the smallest. `dflash-*` files are recognised by `gguf.ts` as their own kind and are never attached or downloaded.
- Loaded models: `fetch_loaded_models` reads `GET /status` `models[].id` (`/v1/models` lists every cached model, not what is loaded). The selector matches names with `shortModelKey` (`unsloth/X:Q4_K_M` and `unsloth/X` match).
- Model settings: stored per model in `model_setting_values` (one row per key; see Backend). Load parameters (`nctx`, `ngl`, `compute`, `powerMode`, `spec*`) are sent with the warmup and with every chat request, so the server does not reload. `grammarString`, `seed` and `think` (`enable_think`) are per-request generation settings. QAIRT (AI Hub) models ignore most of these (`utils/modelSettings.ts`, `loadSettingDisabledReason`). Server options (`origins`, `keepalive`) are app settings in `user_preferences`, not per model; changing them restarts the server.
- Context window: `resolveLoadParams` uses the saved `nctx`, else the model's native `context_size` (`db.loadNativeContext`), else omits `nctx` so the server default applies (4096 per `geniex-cli-reference.md`). `ChatContextHeader` ring and `ModelSettings` display use the same order; `DEFAULT_CONTEXT_WINDOW` (4096) is used only when both are missing.
- Context usage (uncommitted): `contextUsageOf(messages)` takes the last reply that has exact counts (`promptTokens` + `completionTokens`) as the base, then adds chars / 4 for the messages after it, and text-file tokens from those messages. With no counted reply, everything is estimated (text files included; media is not estimated). The total is marked exact only when a counted reply exists. The ring's text-file arc is `fileTokensOf` of all sent text files, capped at the total, so it is an estimate. Stopped replies carry no counts.
- Model save: `ModelSettings` saves, then, if the model is loaded, `services/modelLoad.ts` `reloadModel`: `unloadModels` (stop server, unloads all) -> start server with saved server options -> `load_model` with the saved load params (`savedLoadParams`) -> set active model and the active session's model. A failed reload shows an error toast; the model is left unloaded.
- Settings scan: `ModelSettings` buttons (`utils/settingsButtons.ts`): Scan when the selected model is the loaded one, else Reload & Scan (reloads with saved settings, unloads every model, then scans). Cancel scan while running. The scan does not load models and does not read or write saved settings.
  - Gating from the summary: `thinking` and `toolCalls` skipped when the template hint is false (unknown runs the probe); `vision` skipped when the folder has no projector; `audio` skipped unless the projector says it has an audio encoder (unknown also skips). A skipped key is a `template` result with no request.
  - One plain baseline request first; a refusal there aborts the scan. Then the 14 keys in order, vision and audio last; `capability-scan-progress` before each key. Each probe is `ATTEMPTS` = 2 requests (an inconclusive one is retried once). Probe prompts use temperature 0 and small `max_tokens`; `thinking` uses a reasoning question, with a 200-token cap for thinking off and a 1024-token stream cap for thinking on. The vision and audio probes send an `image_url` and an `input_audio` part with the bundled assets.
  - Results are saved with `model_capabilities::save` (write-once rule). A not-run key loses its row unless it is confirmed. Keys not reached after a cancel keep their rows. Confirmed rows are never stale.
  - Passive evidence: a saved assistant reply that shows a think block records `thinking` as `works` with `source` `conversation`, only when there is no confirmed thinking row yet.
  - Badges in the model selector show only current `works` results (`capabilityBadges`).
- Model load (header): `start_server` if not running or if its server settings (origins, keepalive) differ from the running server's (`serverOptions`; an external server is reused as is) -> `load_model` with the saved load params (1-token warmup request; checks the model is listed) -> active model. Compute change in the header only sets the default for the next message. Unload = stop the server (`unload_all_models`; the only unload mechanism; no per-model unload exists in GenieX).
- System prompt: stored as `systemBlocks` (`SystemPromptBlock`: `text`, `datetime`, `platform`, `file`). `ChatInput` composes it at each send with `composeSystemPrompt` (`utils/systemPrompt.ts`): datetime uses the current time and local zone; platform uses `getPlatformInfo` (cached) plus the chipset read once at startup (`AppBootstrap`, `configGet("chipset")`, into `modelStore`); files are read with `read_text_file` and wrapped in `--- file: name ---` delimiters. An unreadable file is left out and reported in an info toast. The composed text is sent as `systemPrompt` in the chat settings.
- Chat attachments (uncommitted): the attach menu (`ChatInput`) calls `pick_attachment` then `read_attachment`; up to 4 files wait as tiles above the box until sent. Image and audio items are disabled unless the active model's stored scan has a `works` result for `vision` or `audio` (`attachmentGate`); a disabled item shows why. On send, `modelTakesFiles` checks every file in the session against the model's current stored results; a blocked kind gives an error toast and nothing is sent. `historyFor` builds the API history: a user message's text files are inlined with `fileSection` delimiters, its media becomes content parts, and each earlier user message's files are read again from their stored `path` on every turn (`read_attachment`). The new message uses the files already in memory. Any stored file that has no path, or is no longer there, stops the send with a "Message not sent" toast, and the input keeps the text. The message stores `attachments` (name, size, path, chars for text), not contents.
- Chat (streaming): `ChatInput` sends with a `streamId` and the model's settings (`chatSettingsFor`); the request asks for the usage chunk (`stream_options.include_usage`, uncommitted). `chat-chunk`/`chat-done` are matched to `chatStore.activeStream` by id, so tokens go to the session that started the stream. `chat-done` with counts is saved on the reply (`updateMessageUsage`, `promptTokens`/`completionTokens`). Sessions are saved debounced (500 ms, changed sessions only) by `useSessionPersistence`, flushed on unmount. A failed send adds an error message and saves a `chat_errors` row. `useChatStream` buffers `chat-chunk` text and writes it to the store once per animation frame (flushed on `chat-done`); `ChatArea` scrolls instantly while streaming.
- Retry (uncommitted): only the last user message shows Retry, and only when its files have stored paths. `retryMessage` checks the model against the files up to that message, rebuilds the history with the same `historyFor` (files re-read), and only then removes later messages from the store and the database and sends again. A failure leaves the chat unchanged.
- Toasts: only for operations the user waited on (download start/finish/cancel/fail, model load/switch/unload, chat failure, model removal, model settings saved, attachment failures). Not used for background list or conversation loads.
- CLI update: installer-based, see `cli-update.md`.
