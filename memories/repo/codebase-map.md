## Product
- LocalGenie = Tauri 2 desktop UI over Qualcomm's GenieX CLI (`geniex`), which runs local LLMs on CPU/GPU/NPU. Primary target: Windows ARM64.
- Playground (committed; tabs: Text to image, Image to image, Image upscaling, OCR, Speech to text, Text to speech, Audio to audio; all tested in the app by the user on 2026-10-31 except voice cloning, which is untested): text to image and Image to image with three curated models run by stable-diffusion.cpp's `sd-cli`; Image upscaling is `sd-cli` too (CPU only); the speech (incl. voice cloning) and Audio to audio tabs run sherpa-onnx's offline programs (CPU only). Both runtimes are optional, installed from Settings > Runtimes. OCR is the exception: its models are GenieX models (imported like a Models tab download) and run through the GenieX server, not a Playground runtime. Plan and decisions: `memories/research/playground-runtime-plan.md` (not repeated here).
- Model path for Hugging Face GGUF: the app downloads the files itself (`download_file`, into `<Downloads>/<owner--name>/`, resumable via `<file>.part` + HTTP Range), projector first, then the main file, then imports that folder with `geniex pull <repo>:<precision> --model-hub localfs --local-path <dir>` (`import_gguf`). Hub pulls are no longer used by the app.
- Conversation compaction (committed 1116bf1; off by default; main flow tested by the user on 2026-11-02, per `manual-checklist.md`): when a send reaches a threshold share of the chat's context window (50-90%, default 70), the older messages are summarised by the loaded model first, and the summary is stored as a system row before the prompt. See Key flows.
- Model path for Qualcomm AI Hub (committed; code-read 2026-10-28; runtime-unverified). The catalog lists models that have runtime 11 (`GENIEX_QAIRT`, a QAIRT zip) or 12 (`GENIEX_LLAMACPP`, a llama.cpp GGUF on Hugging Face) with at least one asset in the model's release-assets file. Runtime 11: the zip is downloaded into `<Downloads>/aihub--<id>/` by `download_file`, then `import_aihub_zip` runs `geniex pull qualcomm/<Name>:<precision> --model-hub localfs --local-path <zip>` on the zip itself (not extracted); the zip has no header or repo. Runtime 12: the asset is a Hugging Face GGUF URL and goes through the Hugging Face GGUF pipeline (`import_gguf`, source `hf`).
- AI Hub is a read-only catalog with per-asset download, not a full hub integration: the catalog, model detail, model card and per-asset download are live. `ModelInfo.source = "aihub"` still comes from the name fallback `derive_source` only when no stored source exists.

## Stack
React 19 + TS 5.8 + Vite 6, Fluent UI v9 (`@fluentui/react-components`, `@fluentui/react-charts` for the sidebar usage chart), zustand 5, react-router-dom 7 (MemoryRouter), react-markdown + rehype-highlight. Biome for lint/format. Rust: tauri 2 (`tray-icon` feature; `tray.rs`), zip 2 (`deflate` only; runtime archives), bzip2 0.6 (pure-Rust backend; `.tar.bz2` runtime archives), tauri-plugin-shell (capability `shell:allow-open` only; the GenieX CLI is run from Rust, not via the shell plugin), tauri-plugin-dialog (`dialog:allow-open`, used by `pick_text_file` and `pick_attachment`; `dialog:allow-save`, used by the benchmark exports), tauri-plugin-notification `~2.4.0` (f1e5543; `notification:default`; the npm `@tauri-apps/plugin-notification` `~2.4.0` must match it; kept below 2.5 because 2.5+ needs Tauri 2.12, so that upgrade is a Tauri bump first, per the change note), sea-orm 1 (SQLite), tokio, reqwest, sysinfo, base64 0.22 (probe and attachment data), image 0.25 (`jpeg`, `png`, `webp`; attachment scaling), sha2 0.10 (benchmark file SHA-256), prost 0.14 (AI Hub protobuf types). Build: `build.rs` compiles `src-tauri/proto/*.proto` with `protox` 0.10 and `prost-build` 0.14 into `OUT_DIR` (no `protoc` needed). Dev port 1420; GenieX server default port 18181.
Window: frameless (`decorations: false`, background `#292929`); the custom `shell/TitleBar/TitleBar.tsx` provides the chrome. Window-control permissions are in `src-tauri/capabilities/default.json`.
CSP (`src-tauri/tauri.conf.json`): `connect-src 'self' http://127.0.0.1:* ws://127.0.0.1:*` only, with no huggingface.co host. The Hub browser's webview `fetch` calls work in the app (reported); the reason is not established (see known-issues, unresolved). Rust-side `reqwest` calls are not subject to CSP, so the AI Hub catalog and downloads (Rust) need no CSP change; the same holds for runtime archives (GitHub) and Playground model files (Hugging Face). `tauri.conf.json` is unchanged in 31a9e7c and c84c413.

## Optional runtimes and Playground (backend)
- `commands/runtimes/`: the runtime registry. An archive runtime (stable-diffusion.cpp, sherpa-onnx) is a GitHub release archive installed into `<app data>/runtimes/<id>/<tag>/`, with one `installed_runtimes` row per runtime naming the current version (older folders stay on disk). The GenieX CLI is an installer runtime (`InstallKind::Installer`, `geniex.rs`): no folder and no row; its version is read from `geniex version`.
  - `spec.rs`: `RUNTIME_SPECS` = `[GENIEX, SD_CPP, SHERPA_ONNX]` (display order). `GENIEX` (`qualcomm/GenieX`) has no archive layout (`archive_layout()` is an error). An archive runtime's `ArchiveLayout` has `asset_contains`, `asset_excludes`, `asset_suffix`, `archive` (`ArchiveFormat::Zip` | `TarBz2`), `strip_top_level` and `tag_prefix`; `git_tag(version)` gives the release tag of a version (`2.0.1` -> `v2.0.1` for sherpa-onnx), used by an explicit-version install (`runtimes/mod.rs`). `sd-cpp` (stable-diffusion.cpp) comes from `andrew-c0/stable-diffusion.cpp` (`SD_CPP_REPO`; the fork publishes Windows ARM64 builds, upstream does not). An archive matches when its name contains `sd` and `windows-arm64` and ends in `.zip`. The program is `sd-cli.exe`. `sherpa-onnx` comes from `k2-fsa/sherpa-onnx` (`SHERPA_ONNX_REPO`): asset contains `sherpa-onnx-v` and `win-arm64`, excludes `-lib`, `-no-tts`, `-jni`, `static-`, `Debug`, `Release`, `RelWithDebInfo`, and ends in `-shared-MT-MinSizeRel.tar.bz2`; the single top-level folder is dropped on unpack; the checked program is `bin/sherpa-onnx-offline.exe`. `sherpa_cli.rs` (`sherpa_programs`) resolves the install's `bin/` with `sherpa-onnx-offline.exe`, `-offline-tts.exe`, `-offline-denoiser.exe` and `-offline-source-separation.exe` and errors "sherpa-onnx is not installed" when missing.
  - `geniex.rs` (986b5dc): the installer steps. Install looks up the latest release (`releases/latest`, through the release cache), takes its `cli-setup` + `windows-arm64` `.exe`, downloads it into `<app data>/` (the same `.part` and cancel rules as archives), checks GitHub's digest when there is one, runs it with `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART` and no console window, polls `geniex version` every 3 s (100 tries) until it matches the release, then deletes the setup file (best effort). Uninstall stops the server this app started, runs `unins000.exe` beside the binary or in its parent with the same flags (120 s limit), then waits up to 60 s for `geniex version` to stop answering. Both are Windows ARM64 only.
  - `release.rs`: the GitHub lookup shared by the archive runtimes and `geniex.rs` (`fetch_release_json`, `parse_release`, `github_client`). `release_list_api_url` reads 30 releases; drafts and prereleases are dropped; the newest by `published_at` that has the archive wins (`newest_release`). `ReleaseCache` keeps successful lookups for one hour (`RUNTIME_RELEASE_CACHE_SECS`), keyed by API URL or `latest:<repo>:<id>`; failures are not cached. Registered in `lib.rs`.
  - `install.rs`: the download URL must start with `https://github.com/<repo>/releases/download/`. The archive goes to `<runtime>/downloads/` (resumes `.part` through `download.rs` `stream_to_partial`), is checked against GitHub's SHA-256 digest when one is given, unpacked by `archive.rs` `extract` (zip or tar.bz2; entry paths checked against zip-slip, links and special entries refused; optional strip of the single top-level folder) into `.staging-<tag>`, checked for the spec's program, then renamed to `<tag>/`.
  - `store.rs`: reads, writes and forgets the `installed_runtimes` row. `mod.rs` holds the commands and the progress events. An operation on one runtime (install or uninstall) takes the `DownloadRegistry` key `runtime:<id>`, so a second one is refused while it runs.
  - Commands: `runtime_list`, `runtime_check_update(id)` (installed version against the newest matching release; GenieX: the latest stable release), `runtime_install(id, version?)` (no version = newest matching release; GenieX ignores the version; returns the installed version), `runtime_uninstall(id)` (archive: removes the runtime's whole folder and its row; GenieX: runs its uninstaller). Install emits `runtime-install-progress`; uninstall emits no events.
- `commands/playground/` (one domain per module; only catalogue URLs are fetched; the webview picks a model by id):
  - `catalog.rs`: three curated recipes in this order: `sd15-q4` (Stable Diffusion 1.5 Q4_0, one file), `flux2-klein-4b-q4` (FLUX.2 klein 4B Q4_0 with a VAE and the Qwen3-4B text encoder), `z-image-turbo-q4` (Z-Image Turbo Q4_0 with a VAE and the same encoder). Files are `huggingface.co/<repo>/resolve/main/<path>`. Files live under `<app data>/playground-models/<owner--repo>/`, so the shared encoder is kept once. Each recipe has its licence, defaults, the sd-cli flag per file, whether it takes a negative prompt and a CFG scale, and `ImageInput` (`none` | `init` | `reference`, exposed as `imageInput`): `sd15-q4` = init (re-draw), `flux2-klein-4b-q4` = reference (edit), `z-image-turbo-q4` = none.
  - `model_download.rs`: `playground_download_model(modelId)` fetches the missing files one after another into `<name>.part`, renames on success, and requires the exact byte count from the catalog (no hash check). Registered in `DownloadRegistry` as `playground:<id>`, so `cancel_download` takes that id and a delete of the same model is refused meanwhile.
  - `model_delete.rs`: `playground_delete_model(modelId)` returns `freedBytes`. It is refused while an image is being made or the model is downloading. Only files no other downloaded recipe needs are removed, and every path must stay inside `playground-models/`.
  - `devices.rs`: `playground_list_devices` runs `sd-cli --list-devices` (15 s timeout) and reads `name<TAB>description` lines. Kind comes from the name prefix: `cpu` = cpu, `htp`/`hexagon` = npu, `opencl`/`vulkan`/`cuda`/`metal`/`sycl`/`rocm`/`gpu` = gpu, else other. `resolve_backend`: a chosen device must be in the list; a missing or `auto` device is the first CPU device listed; with no CPU listed, no `--backend` is passed and sd-cli chooses.
  - `args.rs`: `build_args` for sd-cli: steps, CFG (a distilled recipe always gets its own default; a model without negative prompt support gets none), seed, and one `--backend` (never pinned per module). `--batched-cfg off` is added for any non-CPU device and always for an init-image job, CPU included (see known-issues). Input: init -> `-i <path> --strength <s>` (0.05..1.0, default 0.6, checked); reference -> `-r <path>` with `--sampling-method euler`; `validate_input_for_model` refuses an input for a `none` model. `ImageRequest` has optional `inputPath` and `strength`.
  - `input_image.rs`: `validate_input_image` (exists, a file, png/jpg/jpeg only, 30 MB cap, canonical path without the verbatim prefix) and `data_url`. The user picks the file, so it may be in any folder.
  - `image_job.rs` and `progress.rs`: one image at a time, held in `PlaygroundJobs` (managed in `lib.rs`, killed on window close). sd-cli's stdout and stderr are split on `\n` and `\r`, classified into phases (`loading`, `encoding`, `sampling`, `decoding`, `saving`); the sampling bar gives step counts and seconds per step. Cancel kills the process (`kill_process`), then `playground-image-done` arrives with `cancelled`. The last lines are kept for an error message.
  - `paths.rs`: output is `<Pictures>/LocalGenie/<prompt slug>-<yyyyMMdd-HHmmss>-<seed>.png`, with a free-name suffix when needed. Images from before that were saved under `<app data>/playground/images/` still open. `playground_read_image` (returns a data URL, 20 MB cap) and `playground_reveal_image` (Explorer, Windows only) accept only paths inside those two folders.
  - `playground_generate_image(request)` checks the request, the model's files and the installed runtime (`installed_program`: row plus file exists), resolves the device (which runs `sd-cli --list-devices`), creates the output path, then starts the job and returns. Progress and the result come as events.
  - `program.rs` (replaces `sd_cli.rs`): `command(program, folder)` builds every runtime program process (sd-cli and sherpa-onnx): runs from the given folder, stdin closed, no console window (Windows), `kill_on_drop`.
  - Speech (sherpa-onnx, CPU only; tested in the app by the user, 2026-10-31, except voice cloning): `speech_catalog.rs` (three recipes: `whisper-tiny-en` and `moonshine-base-en` for speech to text, `kokoro-int8-multi-v1` for text to speech; each is one `.tar.bz2` asset under `github.com/k2-fsa/sherpa-onnx/releases/download/` tags `asr-models` / `tts-models`, unpacked to `playground-models/k2-fsa--sherpa-onnx/<model id>/`, size checked; Kokoro offers the 28 English voices `af_`, `am_`, `bf_`, `bm_`), `speech_download.rs`, `speech_delete.rs`, `speech_args.rs` (program arguments; the text goes last), `speech_job.rs` (one speech job at a time in `SpeechJobs`, killed on window close; phases `loading`, `running`, `saving`), `speech_output.rs` (the transcript is the stdout JSON line that starts `{"lang"`; failure detail from the last output lines), `wav.rs` (duration from the WAV header), `recordings.rs` (checks a recording: WAV only, non-empty, 200 MB cap; removes recordings older than a day on each save), `speech_commands.rs` (the commands under IPC).
  - Audio to audio (sherpa-onnx, CPU; shares the speech job slot, `playground-speech-*` events and `playground_cancel_speech`): `audio_catalog.rs` (three recipes, listed with the speech models: `gtcrn-simple` and `dpdfnet4` denoisers, each a single `.onnx` from the `speech-enhancement-models` release; `spleeter-2stems-int8` source separator, a `.tar.bz2` from `source-separation-models`; `SpeechRecipe.delivery` = `Archive` | `SingleFile`, `speech_catalog.rs` `ALLOWED_RELEASES` lists the tags and endings allowed), `audio_args.rs` (`EnhanceRequest`, `denoise_args`, `separate_args`), `audio_job.rs` (plans the program and outputs: `Cleaned speech`, or `Voice` and `Music and other sounds`; WAVs named from the input file stem and time in `<Music>/LocalGenie/`, a counter on a name clash), `audio_commands.rs` (`playground_enhance_audio`; input must be a WAV).
  - Voice cloning (sherpa-onnx Pocket TTS; built, untested in the app): `pocket-tts-int8` is a fourth speech recipe (Tts, 98,336,520 bytes, `tts-models` tag, licence "Non-commercial (Kyutai Pocket TTS, ONNX export)", English, no voices). `SpeechModel.needsReference` is true for it. `playground_synthesize` takes `referenceAudioPath` (`SpeechSynthesizeRequest`): a cloning model requires a readable non-empty WAV there (`speech_args::checked_reference_audio`) and ignores voice and speed; other models ignore the recording. `synthesize_args` takes a `VoiceChoice` (`Speaker { voice_id, speed }` | `Reference(path)`) and refuses a mismatch; Pocket TTS gets `--reference-audio=<path>`.
  - Image upscaling (`upscale_catalog.rs`, `upscale_args.rs`, `upscale_files.rs`, `upscale_commands.rs`; sd-cli, CPU only because the GPU backend crashes on upscaling): two curated 4x `.pth` models, `realesrgan-x4plus-anime-6b` and `nomos2-hq-mosr-x4`, from GitHub releases (allowed repos `xinntao/Real-ESRGAN`, `Phhofm/models`; size checked), stored in `playground-models/upscalers/`. Input png/jpg, 30 MB, at most 1024 px on the longest side. `playground_upscale_image` runs `sd-cli` with `--upscale-model` and the resolved CPU backend through the image job slot (`ImageJob.result_size`); output `<Pictures>/LocalGenie/upscaled-<timestamp>-<input slug>.png` (`paths::upscaled_stem`). It reuses `playground-image-progress`/`-done`; the done event gains `width` and `height` for an upscale. Downloads reuse `playground-download-*`.
  - OCR (`ocr_catalog.rs`, `ocr_download.rs`, `ocr_job.rs`, `ocr_request.rs`, `ocr_table.rs`, `ocr_commands.rs`; the only Playground tab that goes through GenieX): two curated vision-language GGUF models, `paddleocr-vl-1-6` (BF16; modes text and table) and `minicpm-ocr-1-0` (Q4_K_M; text), each a model file plus projector from Hugging Face. The download uses the shared `model_download::fetch_to_folder` (projector first, `.part` resume, exact size) into `<Downloads>/<folder>/`, then `import_gguf_files`, so the model also shows in the Models tab (`model-pull-*` events, row stored with source `hf`). "Downloaded" = the repo is in `geniex list` (`installed_model_sizes`), else the stored row. Delete removes the model from GenieX (`remove_model`), forgets the row and removes leftovers in Downloads. `playground_ocr_run` needs the picture (png/jpg, 30 MB, at most 2500 px), the model imported and the GenieX server reachable on the given port (`fetch_loaded_models`, else "Start the GenieX server first"); one job at a time (`OcrJobs`, managed in `lib.rs`). The job sends one non-streamed chat completion (image part, then the mode's prompt, temperature 0, `max_tokens` 2048, per-request `compute` and `vit_compute`; Compute `Auto` omits `compute`; vision encoder CPU or NPU `HTP0`), 10 minute timeout, strips think blocks, and converts PaddleOCR-VL table tags to a markdown table (`ocr_table.rs`). Cancel drops the request; the server may keep generating. `playground_save_ocr_text` saves a .txt through `benchmark_runs::save_with_dialog`.
  - Non-ASCII text is converted to ASCII before it reaches sherpa-onnx (`speech_args.rs`: accented Latin letters get their base letter, typographic punctuation an ASCII stand-in, anything else a space), because the command line cannot carry it. Known limitation.
  - Outputs: speech goes to `<Music>/LocalGenie/`; microphone recordings to `<app cache>/playground-audio/`. `playground_read_audio` (data URL) and `playground_reveal_audio` accept only paths inside those two folders.
- `lib.rs` also manages `ReleaseCache`, `PlaygroundJobs`, `SpeechJobs` and `OcrJobs`, and registers the runtime and playground commands (see IPC).
- Downloads shared with the runtimes: `download.rs` exposes `stream_to_partial`, `Transfer`, `TransferProgress`, `validate_file_name` and `DownloadRegistry::{register, release, client}` to them. `download_file`'s signature and URL allowlist are unchanged; Playground model files do not go through `download_file`; `playground/model_download.rs` `fetch_to_folder` (with `FileSource`, `FilePosition`) is the shared one-file download used by the recipe download and by OCR.

## Events (verified by grep of `emit`/listeners)
- `runtime-install-progress` `{ id, stage, received, total, message }` (`InstallProgress`; `stage` = `checking` | `downloading` | `verifying` | `extracting` | `installing` (GenieX only) | `done` | `error`; `received`/`total` 0 when no byte count): emitted by `runtime_install`. Listened to in `components/shell/DownloadDrawer/useDownloadManager.ts` (`installing` shows as "Installing…" in the drawer's import step).
- `playground-download-progress` `{ modelId, fileName, fileIndex, fileCount, received, total }` and `playground-download-done` `{ modelId, status, error? }` (`done` | `error` | `cancelled`): emitted by `playground_download_model`.
- `playground-image-progress` `{ jobId, phase, step, steps, secondsPerStep, message }` (`phase` = `loading` | `encoding` | `sampling` | `decoding` | `saving`) and `playground-image-done` `{ jobId, status, path?, error?, seed, seconds, width?, height? }` (`width`/`height` on a finished upscale only): emitted by the image job (also upscaling).
- `playground-ocr-done` `{ jobId, status, text?, error?, seconds }` (`status` = `done` | `error` | `cancelled`): emitted by the OCR job; there is no OCR progress event. OCR model downloads use `playground-download-*`.
- `playground-speech-progress` `{ jobId, phase }` (`phase` = `loading` | `running` | `saving`) and `playground-speech-done` `{ jobId, kind, status, text?, outputPath?, outputs?, error?, ... }` (`kind` = `stt` | `tts` | `denoise` | `separate`; `outputs` = `[{ label, path }]` for the last two; `status` = `ok` | `cancelled` | `error`; the audio-length field is in `speech_job.rs`): emitted by the speech job (also audio to audio). All seven playground events are listened to in `PlaygroundRuntime/usePlaygroundEvents.ts`.
- `download-progress` `{ id, file, received, total, speed }`, `{ ..., complete: true }`, `{ id, file, cancelled: true }`. `id` = Hugging Face repo id (download id).
- `model-pull-start` `{ model }`, `model-pull-progress` `{ model, message }`, `model-pull-complete` `{ model }`: emitted by `import_gguf` and `import_aihub_zip` (GenieX local import); the frontend listener is the same for both. Listened to in `useDownloadManager.ts`.
- `chat-chunk` `{ streamId, content }`; `chat-done` `{ streamId, finishReason, promptTokens, completionTokens }` (also emitted on user cancel, with `finishReason` `cancelled`). The two counts come from the server's usage chunk and are null when the server sent none, such as after a stop. Other stats are computed in the frontend (`useChatStream.ts`).
- `server-stopped` (no payload; listened to in `useModelLoader`): emitted only when the `geniex serve` child exits without a stop request. Stop and unload clear the tracked PID before killing, so they do not emit it. `server-log` `ServerLogLine` (`ServerLogsCard`).
- `benchmark-progress` (`BenchmarkProgressEvent`, `types/index.ts`: `runId`, `pass`, `totalPasses`, `stepIndex`, `totalSteps`, `promptName`, step state, error): emitted by `benchmark_runner.rs` as each step starts and finishes. Listened to in `SuiteRun/useSuiteRun.ts` (via `listenEvent`).
- `benchmark-finished` (`BenchmarkFinishedEvent` `{ runId, status, error }`): emitted once when the run task ends (after the run row is saved). Listened to in `useSuiteRun.ts`.
- `capability-scan-progress` `{ model, key, index, total }`: emitted by `scan_model_capabilities` before each setting is probed; listened to in `useCapabilityScan.ts`. Each decided result is also written to the server log as a `[probe]` line (`logs::record`).

- Context usage (rewritten in 71d05a4, 2026-11-02): `contextUsageOf(messages)` is an estimate of what the next request carries: from the newest summary on (system lines excluded), a reply adds its `completionTokens` (thinking included; the reply's count is used when it has one), every other message adds chars / 4, and text-file tokens are added. Server `promptTokens` are not used: they count only the tokens processed for that request, so with KV reuse they are far below the context. Images and audio are not counted. The ring's text-file arc is `fileTokensOf` of the sent text files, capped at the total. The header always shows `~`.
- Conversation compaction (1116bf1): `sendPrompt` (`services/chatSend.ts`) computes `compactionDue`: enabled, the chat's window known, and (context before the prompt + the prompt's estimate) * 100 >= window * threshold. If due, `summariseBeforePrompt` (`services/chatCompaction.ts`) takes `summaryInputFor` (the messages before the prompt, from the newest summary on, plus that summary as `previousSummary`) and calls `compact_conversation` with the chat's model and load params (repeated, so no reload) and the window. `chatStore.setCompacting` shows "Summarising the conversation…" and the input's stop button calls `stopSummary` (`cancel_compaction`); the input waits meanwhile. The prompt is then sent with the history after the summary (`promptOnlyHistory`): only the prompt, the summary goes into the system prompt as its own block (`systemPromptWithSummary`). If the server still refuses the prompt as too long (`isContextOverflow`), the same summary runs once and the prompt is sent again. A failed summary shows "Summary failed" and the prompt goes as before; a stopped one ("Summary stopped") sends nothing, and the prompt stays in the chat without a reply. Covered messages and summary rows cannot be deleted or retried (`coveredMessageIds`, `canRemoveFrom`, checked in the store and in `MessageBubble`). Earlier summaries stay in effect when the setting is turned off. Summary text: the model's reply with thinking removed; the summary prompt asks for bullet points under about 300 words.

The new message uses the files already in memory. A stored file that has no path, or is no longer there, is left out of the request (`readStoredFiles`) and named in a "Files not sent" toast. The warning repeats on each send until the message holding that file is deleted, because the history is rebuilt from every message. A file that is present but unreadable still stops the send with "Message not sent", and the input keeps the text. The message stores `attachments` (name, size, path, chars for text), not contents.
- Conversation storage (`7d7b1ed`): a new conversation lives in `chatStore` only and is written once it has a message. `ChatInput` saves the session row before the first message; `useSessionPersistence` skips sessions with no messages. Leaving `/chat` or switching conversations drops empty sessions (`discardEmptySessions`), so an empty draft is never stored. Pinning (`setSessionPinned`) replaces the session object, so it is saved by the same debounced path; `updatedAt` is not changed.
- Benchmark run (`63f1fbc`): `Run` lists the suites (`BenchmarkRun`); a suite's page (`/benchmarks/run/:suiteId`, `BenchmarkRunItem` -> `SuiteRun`) runs it on the loaded model; `RunConsentDialog` confirms. The run's state is in `benchmarkRunStore` and its events come through `BenchmarkRuntime` in `MainLayout`, so it keeps going and reporting when the user leaves the page (navigation redesign, committed 24528c2; the run path is not run in the app per `manual-checklist.md`); the frontend makes the run id and calls `start_benchmark_run`. `prepare` checks the server (`fetch_loaded_models` on the configured port) and the suite, writes the run row, then the task runs the steps in the background. Events drive the UI; `cancel_benchmark_run` stops after the request in flight. Chat, model load and unload return an error until the run ends. Runs are read back from SQLite (`list_benchmark_runs`) in the `Runs` tab; `Compare` charts the runs ticked there. Exports: CSV and PNG through save dialogs; `open_benchmark_export` opens the saved file.
- Benchmark library: a prompt has text, keywords (match rule), and files (copied into app data on import, linked by `benchmark_prompt_files`). Deleting a prompt is refused while a suite step uses it. Files dropped from a saved prompt or suite are removed from disk only when no other prompt or step uses them. Suites reference prompts by step (`benchmark_suite_steps`); deleting a suite keeps its runs (`suite_id` is cleared, `suite_name` kept).
- Chat (streaming): `ChatInput` sends with a `streamId` and the model's settings (`chatSettingsFor`); the request asks for the usage chunk (`stream_options.include_usage`). `chat-chunk`/`chat-done` are matched to `chatStore.activeStream` by id, so tokens go to the session that started the stream. `chat-done` with counts is saved on the reply (`updateMessageUsage`, `promptTokens`/`completionTokens`). Sessions are saved debounced (500 ms, changed sessions only) by `useSessionPersistence`, flushed on unmount. A failed send adds an error message and saves a `chat_errors` row. `useChatStream` buffers `chat-chunk` text and writes it to the store once per animation frame (flushed on `chat-done`); `ChatArea` scrolls instantly while streaming.
- Chat settings and system lines (961d167): per-conversation overrides are stored in `chat_sessions.settings_overrides` (only the keys the chat sets; `cleanOverrides` before save). `ChatInput` merges them over the model's stored settings at send (`applyChatOverrides`); the system prompt override, if set, replaces the model's. The header count of custom settings reads `overrideCount`. Before a prompt, `chatEvents.modelChangeLine` adds a `system` line (`model_changed`, content = JSON with model and compute, plus plain text) when the model or compute target differs from the last reply that has them; `sendTargetFor` resolves the target from the saved load settings, else the header compute. System lines are stored and shown, never sent in the history. Each assistant reply records `compute` (`setActiveStream`).
- Retry: only the last user message shows Retry, and only when its files have stored paths. `retryMessage` checks the model against the files up to that message, rebuilds the history with the same `historyFor` (files re-read; a missing file is left out with the same toast as a send), and only then removes later messages from the store and the database and sends again. A failure leaves the chat unchanged.
- Delete (`MessageBubble.tsx` `removeFrom`): any non-streaming message, user or assistant, can be deleted with every message after it. After a `ConfirmDialog`, `chatStore.removeMessagesFrom` drops them from the store and `db.deleteMessage` (or `db.deleteChatError` for an error row) from the database, one call per removed message. Later sends no longer include their files.
- Toasts: only for operations the user waited on (download start/finish/cancel/fail, model load/switch/unload, chat failure, model removal, model settings saved, attachment failures). Not used for background list or conversation loads.
- GenieX CLI install, update and removal: a runtime with an installer, see `cli-update.md`.
